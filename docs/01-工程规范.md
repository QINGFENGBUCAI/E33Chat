### 1.2 新增 MC 版本清单

按顺序完成，全部打勾后提交：

1. `settings.json` 的 `versions` 数组加入 `<mc>-fabric`
2. 新建 `versions/<mc>-fabric/gradle.properties`，填写 `minecraft_version`、`loader_version`、`fabric_api_version`、`archives_base_name`、`loom_version`、`yarn_build`、`java_version`、`modmenu_version`、`mcVersion`
3. 确认 `versions/<mc>-fabric/src/main/resources/fabric.mod.json` 的 `depends` 区间正确
4. `./gradlew :<mc>-fabric:build` 单独通过
5. 为 API 变动补齐 `//#if MC >= xxxxx` 分支，旧版路径使用 `//$$`
6. `./gradlew build` 全版本通过，主版本测试通过
7. 更新本文件 1.1 版本表与 `CHANGELOG.md`

### 1.3 预处理器约束

- 条件必须是 `MC <op> <5 位或 6 位阈值>`，禁止 `&&`、`||`（ReplayMod 风格预处理器不支持复合条件）
- 每个 `//#if` 必须有对应 `//#endif`，允许 `//#else` 与 `//$$`
- 清理注释时仅可删除普通注释与纯空白行，**不得改动任何 `//#` / `//$$` 行**
- 上述规则由 `PreprocessorDirectiveTest` 自动校验

### 1.4 映射之外：参数语义核验

- `applyMojangMapping` 只做符号改名，不保证参数含义不变：同名同签名的方法在 26.x 可能沿用旧描述符但语义已改
- 涉及 `//#if MC >= 26000` 的行为分支，必须对实机 jar 用 `javap -p -c` 反汇编确认分支走向，不能凭 ≤1.21.11 的语义推断
- 已确认案例 `ChatListener.handleSystemMessage(Component, boolean)`：
  - `true` → `ChatComponent.addServerSystemMessage`（服务端下发的系统消息）
  - `false` → `ChatComponent.addClientSystemMessage`（客户端本地消息）
  - overlay 走独立的 `ChatListener.handleOverlay(Component)`，不经过该布尔参数
  - ≤1.21.11 的 `onGameMessage(Text, boolean)` 布尔参数才是 overlay
- 反例：在 26.x 沿用旧版 `if (overlay) return;` 会跳过所有服务端系统消息，使 NCR 转发的玩家聊天与 `/msg` 私聊全部落到系统消息兜底
- 版本阈值按六位数书写（26.1 = 260100，26.2 = 260200，26.3 = 260300）；`26000` 只用于“26.x 起”的统一分支

## 2. 发布与版本

- 版本号遵循 SemVer：`MAJOR.MINOR.PATCH`，预发布为 `-preN`
- **pre 递增规则**：`mod_version` 是 `MAJOR.MINOR.PATCH-preN` 形态时，每次代码更改 pre 号自动 +1（pre2 → pre3）；发布正式版（去掉 `-preN`）后，下一个修复版回到新 PATCH 号的 `-pre1`。例：`2.4.22-pre1` → 发布 `2.4.22` → 下一个修复 `2.4.23-pre1` → 再修 `2.4.23-pre2`。此递增由 AI 助手在每次代码更改后自动执行，除非用户明确说明“本次暂不递进”
- `gradle.properties` 的 `mod_version` 是唯一版本来源，22 个产物共用
- 已发布的版本号与 jar 不可覆盖重传；修复必须发新版本
- 发布必须包含：22 个 jar、对应 tag、GitHub Release（预发布勾选 prerelease）
- Release 资产附 SHA-256：CI 生成 `checksums.sha256`，发布时一并上传
- Gradle Wrapper 固定版本并校验 `distributionSha256Sum`
- CI 中所有第三方 Action 按 commit SHA 固定，不使用浮动 tag
- 发布前必须完成：全版本构建通过、主版本测试通过、敏感信息扫描 0 命中

## 3. 静态质量

- 所有 `JavaCompile` 启用 `-Xlint:all`，告警不阻断构建
- 纯配置类（`ChatBubbleConfig`、`ConfigManager`、`ServerConfig`、`ServerConfigManager`）不得 import `net.minecraft.*`
- Minecraft 类型只允许出现在 `client/`、`render/`、`mixin/`、`server/` 等适配层
- 跨系统传递的结构化数据使用具体类型，不用裸 `Map<String, Object>` 作为接口参数
- 不引入 spotless / palantirJavaFormat：与现有代码风格冲突，格式化由人工保证

## 4. 测试

测试仅在主版本（`versions/mainProject` 指向的 `1.21.1-fabric`）编译运行。

| 测试类 | 职责 |
|---|---|
| `LangFileTest` | `zh_cn.json` 与 `en_us.json` 键集完全一致 |
| `PreprocessorDirectiveTest` | `//#if` / `//#endif` 配对、条件格式合法、无复合条件 |
| `ResourceIntegrityTest` | `fabric.mod.json` 的 entrypoint 与 mixin 配置引用类均可加载 |
| `PureLogicBoundaryTest` | 纯配置类不依赖 Minecraft |
| 业务测试（10 个类） | 存储、配置、渲染计算、消息解析、模板等 |

约定：

- 新增系统至少有正常路径、非法输入、边界条件各 1 个用例
- 修复缺陷必须补回归测试
- 纯逻辑测试不得依赖游戏客户端启动

## 6. 聊天消息识别约定

- 名称匹配必须跳过装饰性括号内的同名文本（如 chat_heads 注入的 `[Name head]`），以括号外的真实名称位置作为 `nameStart` / `nameEnd`；实现见 `MessagePresentation.findNameIndex`
- 名称后仅有空白的行按广播句处理（`isWhitespaceOnlyGap`）；`>`、`:`、`：` 等分隔符不算空白
- 私聊方向统一判定：
  - `X 悄悄地对你说：…` / `X whispers to you: …` → 入站，sender = X
  - `你悄悄地对 X 说：…` / `You whisper to X: …` → 出站，sender = 本人，partner = X
  - 系统消息通道（NCR / 插件转发）与签名聊天通道使用同一套方向判定
- 修改解析逻辑必须补 `MessagePresentationTest` 或 `WhisperFormatsTest` 回归用例，覆盖带装饰前缀与无分隔符的变体

## 7. 代码注释规范

- 注释只标功能名称：类/接口/enum/record 上方一行 `// 类职责`，每个方法/构造器上方一行 `// 功能名`
- 注释用中文，单行、≤15 字、不加句号，不使用 Javadoc、不写参数/返回值说明
- 不写实现细节、历史背景、调试线索与推导过程；方法体内不逐行注释
- 已有代码中的长段解释注释按上述方式压缩为一行功能名；废弃说明直接删除
- `//#if`、`//#else`、`//#endif`、`//$$` 是构建期源码预处理指令与其它版本的代码，不属于注释，禁止删除或改写
- 新增代码一律按此方式注释；方法改名或行为变化时同步更新对应那一行注释
